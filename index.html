    Cómo se conectan

    1. El contenido visible del portafolio vive en portfolio/src/content/data/*.json y el del CV en curriculum/cv_data.json.
    2. El admin edita esos JSON y publica un solo commit en main a través de una función de Netlify que guarda el token de GitHub.
    3. Ese commit dispara los workflows de GitHub Actions (CV, imágenes, pruebas) y el deploy de Netlify del portafolio.
    4. El formulario de contacto del portafolio envía cada mensaje a una función del admin, que lo guarda y manda los correos.
    5. El README del perfil se regenera aparte (gráficas diarias) y se copia al repositorio público.
    6. Cada lunes, una función programada del admin lee Umami y Search Console y le manda a Harol un resumen de la semana.

    Cómo fluye un cambio

    Desde el admin

    1. Harol entra en admin.hgsportafolio.site con dos factores.
    2. El admin lee los JSON de main a través de una función del servidor, que guarda el token de GitHub.
    3. Al publicar, hace un solo commit en main con todos los archivos e imágenes.
    4. El push a main dispara:
    5. el deploy de Netlify del portafolio, cuyo build corre npm run images (convierte originales a WebP) y tsc --noEmit (valida la forma de cada JSON);
    6. Curriculum, que regenera los PDF y hace commit si cambiaron;
    7. Images, si hay originales nuevos en portfolio/images/, que commitea los WebP y lanza Portfolio CI;
    8. Portfolio CI, si cambió algo en portfolio/**.
    9. El admin sigue las ejecuciones de Actions de ese commit.

    Si un JSON tiene la forma equivocada, el typecheck falla y Netlify no publica esa versión: el sitio se queda con la anterior. Que un check de GitHub Actions bloquee o no el deploy de Netlify depende de la configuración del panel de Netlify, que no está en el repositorio (por confirmar).

    Desde un commit

    Un cambio de código sigue el mismo camino. En un pull request, además, Netlify publica un deploy preview por sitio y preview-comment.yml deja un comentario con el enlace. Ver CI/CD.

    Un mensaje del formulario

    El formulario del portafolio envía JSON a https://admin.hgsportafolio.site/api/contact. Una función del admin lo filtra, lo guarda y envía dos correos por Resend: la copia a Harol y la confirmación al visitante. El portafolio sigue siendo estático; por eso su CSP permite conectarse al dominio del admin.

    El resumen semanal

    Cada lunes a las 8:00 de Bogotá, Netlify corre una función programada en el sitio del admin: lee la semana anterior en Umami Cloud y Search Console y envía un correo por Resend. No depende de ningún commit.

    El perfil de GitHub

    Va por un camino aparte: Metrics y Privacity actualizan README.md, README.es.md y las gráficas en este repo, y Publish profile copia esos archivos al repositorio público DevCat-HGS/DevCat-HGS. Ver perfil de GitHub.

    El espejo del código

    Cada push a main que toque el sitio corre Publish code, que copia una lista blanca de archivos (portfolio/, seis workflows y un README propio) al repositorio público DevCat-HGS/hgsportafolio. Ese es el código que enlazan los botones «Ver código» del caso y de la franja del portafolio. Ver CI/CD.

    Validación

    JSON pierde los tipos literales, así que checked() en src/content/json.ts compara cada archivo con una copia «ensanchada» del tipo real (Widen<T>). Una clave que falta o está mal escrita hace fallar tsc y, por tanto, el build. Así un dato roto nunca llega a publicarse.

    projects.ts normaliza las entradas: el admin puede dejar campos opcionales como "" o null, y projectsFrom() los quita antes de llegar a los componentes. hidden: true deja el proyecto en el archivo pero fuera del sitio; featured: true lo pone entre los destacados; own: true lo saca de la cuadrícula y lo muestra como franja de proyecto propio.

    Idiomas

    • Español en / y inglés en /en/: dos páginas estáticas con su propio título, descripción, canonical, hreflang, Open Graph, datos estructurados y texto de respaldo.
    • La URL decide el idioma (useLocale, public/splash.js y el build usan la misma regla). El botón cambia sin recargar y actualiza la dirección.
    • portfolio/netlify.toml redirige (302) / a /en/, /migozz/ a /en/migozz/, /aria/ a /en/aria/, /devpanel/ a /en/devpanel/ y /portafolio/ a /en/portafolio/ solo si el navegador pide inglés o tiene la cookie nf_lang=en. El botón de idioma fija esa cookie, que Netlify lee antes que el idioma del navegador. Los rastreadores no mandan idioma y reciben la versión en español. La regla de /aria/ llegó en 574e51b y la de /devpanel/ en 90ff404 y la de /portafolio/ en 433174c (ver dominio y SEO).

    Seguridad

    Seguridad del sitio y del admin

    CSP y cabeceras del sitio, el formulario de contacto, los SVG saneados, dependencias, búsqueda de secretos y qué código se publica.

    4 min de lectura · seguridad.md

    Principio

    El admin es privado y se entra con dos factores; su detalle no se publica. El token de GitHub nunca llega al navegador: los commits salen de una función del servidor. Antes del commit bf84696 (2026-10-21) el admin pedía el token en el navegador; ese modelo ya no existe.

    Cabeceras del portafolio

    portfolio/seo/headers.ts es la única fuente: vite preview las sirve para las pruebas y el build las escribe en dist/_headers para Netlify.

    • CSP sin scripts en línea ni unsafe-eval. Por eso los scripts de la pantalla de bienvenida y del 404 son archivos (public/splash.js, public/404.js). style-src admite 'unsafe-inline' por los bloques <style> de index.html y los atributos style de React.
    • connect-src permite 'self' y https://admin.hgsportafolio.site (CONTACT_ORIGIN en src/lib/endpoints.ts), porque el formulario de contacto envía ahí. La misma constante alimenta el formulario y la política, así no se desalinean.
    • Si VITE_UMAMI_WEBSITE_ID trae un UUID válido, la CSP abre solo los orígenes de Umami: https://cloud.umami.is en script-src y, en connect-src, además https://gateway.umami.is (adonde el script envía los eventos desde el commit 7837484) y https://api-gateway.umami.dev (el host anterior). Sin UUID, la analítica está apagada y la CSP no abre nada.
    • nosniff, X-Frame-Options: DENY, Referrer-Policy: strict-origin-when-cross-origin, Permissions-Policy, COOP y HSTS.

    e2e/seo.spec.ts comprueba que cada página envía la política y corre sin violaciones.

    El admin tiene su propia política, más cerrada, y no se indexa.

    Formulario de contacto

    El formulario del portafolio le escribe al admin (POST https://admin.hgsportafolio.site/api/contact), que manda los correos con Resend. Es la ruta del admin que atiende al público, y se protege así:

    • Origen: solo acepta el portafolio, su dirección de Netlify y sus deploy previews; las cabeceras CORS solo se envían a esos orígenes.
    • Bots: un campo trampa invisible y un tiempo mínimo de llenado. Los bots reciben la misma respuesta que una persona.
    • Límites: tiene un tope de mensajes por dirección y por día.
    • Confirmación sin eco: el correo al visitante nunca repite lo que escribió (ni el mensaje, ni un nombre que no parezca nombre), para que el formulario no sirva para mandar texto a desconocidos.

    Íconos SVG subidos desde el admin

    Cada SVG se limpia antes del commit: se quitan scripts, manejadores on*, enlaces externos y javascript:, documentos incrustados y estilos con @import o URL externas, y se rechazan archivos de más de 25 KB (commit 2d942c4). La CSP del portafolio ya bloquea scripts en línea; esto cierra el caso de alguien que abra el SVG directamente.

    security.txt

    portfolio/public/.well-known/security.txt (RFC 9116) dice a quién avisar de un problema de seguridad. Tiene fecha de vencimiento: tests/security-txt.test.ts falla un mes antes, como recordatorio para renovarla.

    Dependencias

    • Dependabot revisa cada semana portfolio/, admin/ y las acciones de GitHub (ver CI/CD). Según el mensaje del commit 2d942c4, las alertas de vulnerabilidades y los arreglos automáticos de seguridad de Dependabot están activados en portfolio-hgs (configuración de GitHub, fuera del código).
    • Vite 8.3.5 (commit f3089f8, 2026-10-21): el portafolio y el admin subieron a esa versión, que cerró las 12 alertas abiertas de Dependabot (servidor de desarrollo de Vite y launch-editor). Las ramas de Dependabot .../vite-8.3.5 siguen en el remoto, ya sin PR abierto.

    Búsqueda de secretos

    El escaneo de secretos de GitHub no está disponible en repos privados del plan gratuito, así que .github/workflows/secret-scan.yml corre gitleaks sobre todo el historial en cada push a main o desarrollo y en cada pull request. Si encuentra una clave o un token, el check falla y el valor sale tapado en el registro. Según el commit 2d942c4, el historial actual sale limpio.

    El mismo commit registra reglas de GitHub (fuera del código) que impiden borrar o reescribir con force-push la rama main en DevCat-HGS y DevCat-HGS.github.io.

    Qué código es público

    El 2026-10-21 se revisó el historial de portfolio-hgs para ver si podía pasar a público. No hay credenciales (coincide con gitleaks), pero el historial guarda archivos que salieron del árbol y no deben publicarse, y GitHub conserva cada PR en referencias refs/pull/* que el dueño no puede borrar, así que reescribir el historial no basta.

    Por eso este repositorio sigue privado y, desde el commit 5795692 (2026-10-22), el código del sitio se publica en un repositorio nuevo, DevCat-HGS/hgsportafolio: un espejo de solo lectura con historial propio, armado con una lista blanca que nunca incluye el admin, los datos del CV ni el perfil, y con una revisión final que aborta la publicación si se cuela una ruta privada. Detalle en CI/CD.

    La documentación sigue la misma idea: lo que se publica en docs.hgsportafolio.site es una edición que deja fuera cómo está hecho el admin.

    Regla para el código público

    Solo se publica código propio. Los repos de clientes se quedan privados (ver perfil de GitHub). Los repos públicos de proyectos de formación se publican como copias nuevas en un solo commit, sin archivos .env, direcciones del servidor ni contraseñas, nunca cambiando la visibilidad del repo original, cuyo historial puede guardar credenciales.

    Lo que nunca llega al navegador

    Los secretos solo los leen las funciones del servidor, y los archivos .env están en .gitignore; solo se versionan las plantillas .env.example, sin valores secretos.

    Fuente única en cv_data.json, generación automática de los PDF en español e inglés y las decisiones para pasar filtros ATS.

    2 min de lectura · curriculum.md

    Fuente única

    curriculum/cv_data.json es la única fuente del CV. Tiene los datos de contacto y, por idioma (es y en): title, location, labels, summary, experience, skills, projects, education, certifications y awards. La clave files dice el nombre del PDF de cada idioma.

    Se edita desde el admin o a mano.

    Generación

    curriculum/generate_cv.py usa ReportLab y escribe:

    SalidaPara qué
    curriculum/output/Harol_Guerrero_CV_ES.pdf y _EN.pdfFuente versionada de los PDF.
    portfolio/public/cv/ (mismos nombres)Copia que descarga el botón del portafolio.
    pip install -r curriculum/requirements.txt
python curriculum/generate_cv.py

    Opciones: --data (otro JSON), --out (otra carpeta), --site-dir (otra carpeta para la copia) y --no-site-copy.

    El PDF es determinista (invariant=1): si cv_data.json no cambió, el archivo sale idéntico y no hay commit.

    Automático

    El workflow .github/workflows/curriculum.yml corre en cada push a main o desarrollo (salvo cuando solo cambian los propios PDF) y a mano. Instala ReportLab, genera los PDF y, si cambiaron, hace commit chore: update CV y push a la misma rama.

    portfolio/netlify.toml sirve /cv/* con must-revalidate, así el visitante siempre baja la última versión.

    Pensado para ATS

    • Una sola columna, sin tablas ni imágenes.
    • Texto real y seleccionable: la fuente Inter (curriculum/fonts/, licencia OFL) va incrustada con su mapa Unicode, así el texto se puede extraer.
    • Encabezados convencionales y fechas con formato uniforme.
    • Metadatos del PDF (título y autor) completos.
    • Colores sobrios, legibles también en blanco y negro.

    Regla de contenido: solo lo que se hizo

    El CV describe lo construido y medido, no lo planeado. Ejemplo del commit 8bbfdbf (2026-10-21): el proyecto ARIA decía que el asistente buscaba en OpenSearch y escalaba casos a un consultor humano, y ninguna de las dos cosas se construyó. Ahora dice que fue trabajo de un equipo de cinco personas, cuál fue la parte de Harol (interfaz de chat en React con respuestas en vivo y panel de fuentes, una API de pruebas en FastAPI y el pipeline batch), el stack real (Bedrock y RAG sobre S3 Vectors, en AWS serverless) y un tiempo de respuesta medido. OpenSearch salió también de la lista de habilidades. El texto coincide con la tarjeta y el caso de ARIA del portafolio (ver portafolio).

    El JSON incluye teléfono y correo porque van impresos en el CV. Esta documentación no los repite.

    Redirección por idioma

    En portfolio/netlify.toml, / redirige con un 302 a /en/ solo cuando el navegador pide inglés o tiene la cookie nf_lang=en (condición Language = ["en"], que Netlify evalúa leyendo primero esa cookie).     Por qué Google muestra un globo y no el favicon

    En los resultados de Google el sitio aparece con un globo genérico. El favicon está bien: public/favicon.ico (48 × 48), favicon-192.png, favicon.svg y apple-touch-icon.png existen y se declaran en el <head> de cada página (commit 4f652c0). Google guarda y actualiza los favicones con un rastreador aparte y a su propio ritmo, así que el globo puede tardar días o semanas en cambiar después de que el ícono es correcto. No hace falta tocar el código; pedir la indexación de la portada en Search Console puede acelerarlo.
