Cómo se conectan

  1. El contenido visible del portafolio vive en portfolio/src/content/data/*.json y el del CV en curriculum/cv_data.json.
  2. El admin edita esos JSON y publica un solo commit en main a través de una función de Netlify que guarda el token de GitHub.
  3. Ese commit dispara los workflows de GitHub Actions (CV, imágenes, pruebas) y el deploy de Netlify del portafolio.
  4. El formulario de contacto del portafolio envía cada mensaje a una función del admin, que lo guarda y manda los correos.
  5. El README del perfil se regenera aparte (gráficas diarias) y se copia al repositorio público.

Dos sitios de Netlify

  • portafolio-hgs construye portfolio/ con portfolio/netlify.toml (npm run images && npm run build, publica dist).
  • admin-hgs construye admin/ con admin/netlify.toml (base directory admin). Su ignore (git diff --quiet $CACHED_COMMIT_REF $COMMIT_REF -- .) hace que solo se reconstruya cuando cambia la carpeta admin/, no con cada cambio de contenido.

Van separados para que el admin tenga su propia política de seguridad y no se republique con cada cambio de contenido (comentario en admin/netlify.toml).

Cómo fluye un cambio

Desde el admin

  1. Harol entra en admin.hgsportafolio.site (PIN y código por correo, ver seguridad).
  2. El admin lee los JSON de main por /api/github.
  3. Al publicar, el navegador manda a /api/github las llamadas de la Git Data API: blobs, árbol, commit y mover refs/heads/main. Resultado: un solo commit con todos los archivos e imágenes (admin/src/github.ts).
  4. El push a main dispara:
  5. el deploy de Netlify del portafolio, cuyo build corre npm run images (convierte originales a WebP) y tsc --noEmit (valida la forma de cada JSON);
  6. Curriculum, que regenera los PDF y hace commit si cambiaron;
  7. Images, si hay originales nuevos en portfolio/images/, que commitea los WebP y lanza Portfolio CI;
  8. Portfolio CI, si cambió algo en portfolio/**.
  9. El admin sigue en su tablero de salida las ejecuciones de Actions de ese commit.

Si un JSON tiene la forma equivocada, el typecheck falla y Netlify no publica esa versión: el sitio se queda con la anterior. Que un check de GitHub Actions bloquee o no el deploy de Netlify depende de la configuración del panel de Netlify, que no está en el repositorio (por confirmar).

Desde un commit

Un cambio de código sigue el mismo camino. En un pull request, además, Netlify publica un deploy preview por sitio y preview-comment.yml deja un comentario con el enlace. Ver CI/CD.

Un mensaje del formulario

El formulario del portafolio envía JSON a https://admin.hgsportafolio.site/api/contact. La función del admin lo filtra, lo guarda en Netlify Blobs (almacén contact-messages) y envía dos correos por Resend. Harol lo lee en su correo y en la estación «Mensajes» del admin. El portafolio sigue siendo estático; por eso su CSP permite conectarse al dominio del admin. Ver correos.

Validación

JSON pierde los tipos literales, así que checked() en src/content/json.ts compara cada archivo con una copia «ensanchada» del tipo real (Widen<T>). Una clave que falta o está mal escrita hace fallar tsc y, por tanto, el build. Así un dato roto nunca llega a publicarse.

projects.ts normaliza las entradas: el admin puede dejar campos opcionales como "" o null, y projectsFrom() los quita antes de llegar a los componentes. hidden: true deja el proyecto en el archivo pero fuera del sitio; featured: true lo pone entre los destacados.

Las pruebas de tests/content.test.ts añaden: misma estructura en los dos idiomas, ningún texto vacío, ids de proyectos iguales en ambos idiomas, enlaces solo https, y que existan las imágenes, íconos y PDF referenciados.

Idiomas

  • Español en / y inglés en /en/: dos páginas estáticas con su propio título, descripción, canonical, hreflang, Open Graph, datos estructurados y texto de respaldo.
  • La URL decide el idioma (useLocale, public/splash.js y el build usan la misma regla). El botón cambia sin recargar y actualiza la dirección.
  • portfolio/netlify.toml redirige (302) a /en/ a quien llega por primera vez con el navegador en inglés. El botón de idioma fija la cookie nf_lang, que Netlify lee antes que el idioma del navegador. Los rastreadores no mandan idioma y reciben /.

Admin

El admin, la cabina de control del contenido

Para qué sirve el editor de admin.hgsportafolio.site, qué se edita en cada estación y cómo se revisa y publica un cambio.

5 min de lectura · admin.md

El admin es un editor propio en React + Vite (admin/), con la misma identidad de línea de metro del portafolio. Lee y guarda directamente en este repositorio, así que Harol cambia textos, proyectos, credenciales, stack, CV, MIGOZZ y SEO sin tocar código. También recibe los mensajes del formulario de contacto del portafolio y envía sus correos (ver correos). Se despliega como segundo sitio de Netlify (admin-hgs) en admin.hgsportafolio.site.

Reemplazó el 2026-10-21 a un primer editor basado en Sveltia CMS (commits 3a1e1e4 y c1629bf).

Entrar

  1. Escribir el PIN.
  2. Escribir el código de 6 dígitos que llega al correo del dueño (vence en 10 minutos).
  3. Queda abierta una sesión de 12 horas en una cookie que la página no puede leer.

Si la sesión termina mientras se edita, el admin vuelve a la entrada y los cambios sin publicar siguen guardados en el navegador. El detalle y los límites están en seguridad.

Mensajes

La primera estación no edita archivos. admin/src/components/Inbox.tsx pide a GET /api/messages (admin/netlify/functions/messages.mts) los mensajes que dejó /api/contact en el almacén contact-messages, del más nuevo al más viejo (hasta 200).

  • Cada mensaje muestra nombre, correo, fecha y hora de Bogotá, lugar aproximado (geolocalización de Netlify) e idioma de la página.
  • Responder abre el correo con el asunto «Re: tu mensaje» o «Re: your message», según el idioma.
  • Borrar pide confirmación y llama a DELETE /api/messages/:id. No se puede deshacer.
  • Actualizar vuelve a traer la lista. Si la sesión terminó, la estación lo dice y hay que recargar.

Cada mensaje también llega por correo; esta estación es el archivo, y conserva el mensaje aunque el correo falle.

Cómo se edita

  • Los campos salen de los propios datos: si se agrega una clave a un JSON, el admin la muestra sola. schema.ts solo pone nombres en español, ayudas, campos de solo lectura, listas de opciones y editores especiales.
  • Español e inglés van lado a lado. Las listas permiten agregar, subir, bajar y quitar elementos; un elemento nuevo copia las claves que comparten los existentes, vacías.
  • Las estaciones con cambios sin publicar se pintan de amarillo en el mapa.

Borradores

Lo que no se alcanza a publicar se guarda en localStorage (clave hgs-admin-draft:<rama>), junto con la versión del archivo sobre la que se editó. Al volver, si el archivo en GitHub no cambió, el admin recupera el borrador y lo avisa. Si cambió, el borrador se descarta. El navegador avisa antes de cerrar la pestaña con cambios pendientes.

Las imágenes subidas no se guardan como borrador: solo viven hasta recargar.

Revisar y publicar

El tablero de salida (abajo, components/Departure.tsx) cuenta los cambios y ofrece:

  • Revisar: cada cambio con su antes y ahora, y un aviso de los textos que quedaron vacíos. Permite escribir el mensaje del commit; si se deja vacío, usa content: actualizar <estaciones> desde el admin.
  • Publicar: un solo commit en la rama con todos los archivos e imágenes, hecho con la Git Data API (blobs → árbol → commit → mover la rama). Si la rama se movió entretanto (por ejemplo el commit del CV), reintenta hasta 3 veces sobre la cabeza nueva.
  • Conflictos: si alguien cambió en GitHub uno de los archivos editados desde que se abrió, no publica nada y ofrece «Recargar <archivo>», que trae la versión nueva y descarta los cambios de ese archivo.
  • Seguimiento: después de publicar, el tablero consulta cada 10 segundos (hasta 20 minutos) las ejecuciones de GitHub Actions de ese commit y muestra su estado.

Si GitHub rechaza la publicación, el tablero lo explica: ante un 401 la sesión terminó y hay que entrar de nuevo (los cambios siguen guardados como borrador); ante un 403 el token del servidor (ADMIN_GITHUB_TOKEN en Netlify) no tiene permiso «Contents: Read and write».

Netlify pone el sitio en línea en uno o dos minutos. Si un JSON quedó con la forma equivocada, el build falla y el sitio sigue con la versión anterior (ver arquitectura).

Seguridad

Seguridad del admin y del sitio

Entrada con PIN y código por correo, sesiones, límites, intermediario de GitHub con lista de llamadas permitidas, CSP, cabeceras y protección del formulario.

6 min de lectura · seguridad.md

Principio

El token de GitHub nunca llega al navegador. Vive en Netlify (ADMIN_GITHUB_TOKEN) y solo lo usa la función /api/github, para sesiones abiertas y para una lista cerrada de llamadas. Antes del commit bf84696 (2026-10-21) el admin pedía el token en el navegador; ese modelo ya no existe.

Las reglas están en admin/netlify/lib/auth.ts, escritas como lógica pura con dependencias inyectadas (almacén, correo, reloj) para probarlas sin Netlify en portfolio/tests/admin-auth.test.ts.

Entrada en dos pasos

PasoRutaQué pasa
PINPOST /api/auth/pinCompara el PIN con ADMIN_PIN en tiempo constante. Si es correcto, genera un código de 6 dígitos uniforme, guarda solo su HMAC, lo envía a ADMIN_EMAIL y pone la cookie hgs_challenge (10 minutos, solo para /api/auth).
CódigoPOST /api/auth/codeVerifica la cookie de reto y el código. Si es correcto, gasta el reto y abre una sesión de 12 horas en la cookie hgs_session.
SesiónGET /api/auth/sessionDice si el navegador tiene una sesión válida.
SalirPOST /api/auth/logoutBorra la sesión del almacén y la cookie.

Por qué dos pasos: un PIN corto tiene pocos valores posibles (uno de 4 dígitos, 10.000). Aun acertándolo, solo se envía un código al correo del dueño, así que el PIN solo nunca abre el editor (comentario de auth.ts).

El correo con el código dice desde qué lugar e IP se pidió (geolocalización de Netlify) y avisa que, si no fue Harol, alguien conoce el PIN y hay que cambiar ADMIN_PIN. La pantalla de entrada muestra la dirección de destino enmascarada (maskEmail), suficiente para reconocerla pero no para leerla.

Cómo elegir el PIN

Los límites frenan a quien prueba PIN al azar, no a quien lo adivina en pocos intentos. Por eso ADMIN_PIN no debe poder deducirse de datos públicos del dueño: ni los números de nombres de usuario actuales o anteriores, ni fechas, teléfonos o años que aparezcan en el sitio, el CV o las redes. Conviene un PIN sin relación con nada publicado y de más de 4 dígitos (el mínimo que pide admin/.env.example). Se cambia en las variables de entorno del sitio admin-hgs en Netlify.

Límites

Definidos en LIMITS (admin/netlify/lib/auth.ts):

LímiteValor
PIN fallidos por dirección IP5, luego bloqueo de 15 minutos para esa dirección
PIN fallidos en total (todas las direcciones)20 en una hora, luego bloqueo del paso del PIN para todos durante 1 hora
Vida del código10 minutos
Intentos por código5, luego el código se quema y hay que pedir otro
Espera entre códigos30 segundos por dirección
Duración de la sesión12 horas

Cuando se produce un bloqueo, llega un correo de aviso al dueño una vez por bloqueo. Los contadores, retos y sesiones se guardan en Netlify Blobs (almacén admin-auth) con consistencia fuerte, para que un bloqueo o un código gastado se vean en la petición siguiente (admin/netlify/lib/netlify.ts).

Sesiones

  • Cookie hgs_session con HttpOnly, Secure, SameSite=Strict y Path=/.
  • El valor lleva id, vencimiento y firma HMAC-SHA256 con SESSION_SECRET (mínimo 32 caracteres).
  • La sesión también existe en el almacén: «Salir» la borra, así que una cookie copiada deja de servir.
  • Cambiar SESSION_SECRET cierra todas las sesiones abiertas.
  • Sin ADMIN_PIN o sin un SESSION_SECRET de 32+ caracteres, la función responde 503 y nadie entra.

Intermediario de GitHub

admin/netlify/functions/github.mts atiende /api/github/* y reenvía a api.github.com agregando el token. Antes revisa:

  1. Que la petición traiga X-Requested-With: hgs-admin (fromAdmin). Un formulario de otro sitio no puede poner esa cabecera.
  2. Que haya una sesión válida (si no, 401 y el admin vuelve a la entrada).
  3. Que la llamada esté permitida por allowedGitHubCall:
MétodoRutas permitidas
GET/user, /repos/DevCat-HGS/portfolio-hgs y todo lo que cuelga de ella
POST.../git/blobs, .../git/trees, .../git/commits
PATCH.../git/refs/heads/<rama>

Nada más: ni borrar, ni configuraciones, ni otros repositorios. Rutas con .. o que no empiezan con / se rechazan. Las respuestas salen con Cache-Control: no-store.

El token recomendado en admin/.env.example es fine-grained, solo para el repo portfolio-hgs, con permiso «Contents: Read and write». El admin comprueba al cargar que tenga permiso de escritura.

Cabeceras del admin

En admin/netlify.toml, para todas las rutas:

  • Content-Security-Policy: default-src 'self', script-src 'self', connect-src 'self' (la interfaz solo habla con sus funciones), imágenes de self, data:, blob:, https://hgsportafolio.site y https://avatars.githubusercontent.com, frame-ancestors 'none'.
  • X-Robots-Tag: noindex, nofollow, X-Frame-Options: DENY, X-Content-Type-Options: nosniff, Referrer-Policy: no-referrer, Permissions-Policy restrictiva, Cross-Origin-Opener-Policy: same-origin, Strict-Transport-Security de un año con subdominios.

Cabeceras del portafolio

portfolio/seo/headers.ts es la única fuente: vite preview las sirve para las pruebas y el build las escribe en dist/_headers para Netlify.

  • CSP sin scripts en línea ni unsafe-eval. Por eso los scripts de la pantalla de bienvenida y del 404 son archivos (public/splash.js, public/404.js). style-src admite 'unsafe-inline' por los bloques <style> de index.html y los atributos style de React.
  • connect-src permite 'self' y https://admin.hgsportafolio.site (CONTACT_ORIGIN en src/lib/endpoints.ts), porque el formulario de contacto envía ahí. La misma constante alimenta el formulario y la política, así no se desalinean.
  • Si se define VITE_UMAMI_WEBSITE_ID, la CSP abre solo los orígenes de Umami (https://cloud.umami.is y https://api-gateway.umami.dev); sin él, la analítica está apagada.
  • nosniff, X-Frame-Options: DENY, Referrer-Policy: strict-origin-when-cross-origin, Permissions-Policy, COOP y HSTS.

e2e/seo.spec.ts comprueba que cada página envía la política y corre sin violaciones.

Formulario de contacto

El formulario del portafolio le escribe al admin (POST https://admin.hgsportafolio.site/api/contact). Junto con la entrada (/api/auth/*), es la única ruta del admin que responde sin sesión, y se protege así:

  • Origen: allowedOrigin en admin/netlify/lib/contact.ts solo acepta el portafolio, su dirección de Netlify y sus deploy previews; las cabeceras CORS solo se envían a esos orígenes. Una prueba comprueba que un dominio que imita el nombre (...netlify.app.evil.example) se rechaza.
  • Bots: campo trampa website y tiempo mínimo de llenado de 2,5 segundos. Los bots reciben la misma respuesta que una persona.
  • Límites: 3 mensajes por IP cada 10 minutos y 40 por día en total.
  • Confirmación sin eco: el correo al visitante nunca repite lo que escribió (ni el mensaje, ni un nombre que no parezca nombre), para que el formulario no sirva para mandar texto a desconocidos.

Los mensajes guardados solo se leen y se borran con sesión abierta: admin/netlify/functions/messages.mts (GET /api/messages, DELETE /api/messages/:id) exige la cabecera X-Requested-With: hgs-admin y una sesión válida, igual que el intermediario de GitHub. El borrado solo acepta ids de letras, números, _ y -.

Detalle en correos.

Lo que nunca llega al navegador

  • ADMIN_GITHUB_TOKEN, ADMIN_PIN, SESSION_SECRET, RESEND_API_KEY.
  • Las cookies de sesión y de reto (son HttpOnly).
  • El código de acceso en claro: el servidor solo guarda su HMAC.

Los archivos .env están en .gitignore; solo se versionan las plantillas .env.example, sin valores secretos.

Formulario de contacto

El recorrido

  1. El visitante llena el formulario de la sección Cierre (portfolio/src/components/ContactForm.tsx): nombre (máx. 120), correo (máx. 200) y mensaje (máx. 4000).
  2. El formulario envía JSON por fetch a https://admin.hgsportafolio.site/api/contact (constante CONTACT_API en portfolio/src/lib/endpoints.ts), sin recargar la página. Además de los campos manda lang (idioma de la página), website (campo trampa, invisible) y elapsed (milisegundos desde que se abrió la página hasta el envío). Si la respuesta no es correcta, el formulario pide escribir por correo.
  3. Responde admin/netlify/functions/contact.mts. Solo acepta orígenes del portafolio (allowedOrigin) y contesta las peticiones CORS previas (OPTIONS).
  4. receiveContact() en admin/netlify/lib/contact.ts descarta bots, valida, aplica los límites, guarda el mensaje en Netlify Blobs (almacén contact-messages, clave msg:<id>) y envía los dos correos en paralelo.
  5. El mensaje queda en la estación «Mensajes» del admin aunque falle el envío de los correos (ver admin).

Por qué cambió: el formulario anterior usaba Netlify Forms, que no detectaba el formulario (respondía 404) y redirigía los envíos de la página en inglés, así que no se guardaba ni se enviaba nada (mensaje del commit f4be780).

Los dos correos

  • A Harol: asunto «Nuevo mensaje de <nombre> desde el portafolio», con el nombre, el correo, el mensaje escapado, la fecha en hora de Bogotá y el idioma de la página. «Responder» va directo al visitante (reply_to).
  • Al visitante: «Recibí tu mensaje» o «I got your message», según el idioma de la página. Agradece, dice que la respuesta llega en uno o dos días hábiles y firma Harol. «Responder» va a Harol.

La copia de Harol se envía primero en la lista, pero los dos van con Promise.allSettled: si uno falla, el otro sale igual y el error queda en el registro de la función.

Correos del admin

Los arma admin/netlify/lib/auth.ts y los envía send() en admin/netlify/lib/netlify.ts.

  • Código de acceso: asunto «<código> es tu código del admin», con el código en grande, la advertencia de que vence en 10 minutos, y el lugar, la IP y la hora (Bogotá) de la petición. El pie dice que, si no fue Harol, alguien conoce el PIN y hay que cambiar ADMIN_PIN.
  • Intentos fallidos: asunto «Intentos fallidos en el admin». Avisa si se bloqueó una dirección 15 minutos tras 5 intentos o si se bloqueó el PIN para todos durante una hora. Se envía una vez por bloqueo.

Si el envío del código falla, el reto se borra y la pantalla muestra «No se pudo enviar el código. Revisa RESEND_API_KEY.». Un fallo al enviar el aviso de bloqueo se ignora para no romper la respuesta.

Límites que frenan el abuso: un código cada 30 segundos por dirección y los bloqueos del PIN descritos en seguridad.

Dominio, DNS y posicionamiento

El dominio hgsportafolio.site en Hostinger y Netlify, Search Console, sitemap, canonical, hreflang y datos estructurados.

Dominio

  • Producción: https://hgsportafolio.site, fijado en portfolio/netlify.toml como VITE_SITE_URL. De ahí salen canonical, hreflang, Open Graph, JSON-LD y sitemap.
  • Respaldo: portafolio-hgs.netlify.app sigue abierto. No compite en Google porque cada página declara como canonical su versión en hgsportafolio.site (commit 8d5a3db, que quitó la redirección 301 añadida en 73be47d).

El registrador y el DNS están en Hostinger. Los registros del dominio raíz hacia Netlify no están escritos en el repositorio (por confirmar en el panel de Hostinger).

Registros para Resend

Para que salgan los correos, hgsportafolio.site debe estar verificado en Resend: Resend entrega unos registros DNS (normalmente SPF, DKIM y, opcional, DMARC) que se agregan en Hostinger. Esos registros no están en el repositorio; es un paso pendiente de Harol. Ver configuración.

Search Console

seo.json → site.verification guarda dos códigos de verificación de Google Search Console, que se emiten como <meta name="google-site-verification"> en cada página. Se editan en el admin, estación SEO. Sus valores no se copian aquí.
